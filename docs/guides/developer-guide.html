    Part A

    Foundations

    What the product is, the WhatsApp concepts you must understand, and the technology choices.

    1. The big picture in plain words

    The kit is one web application that you run on a server. It does three jobs at the same time:

    🤖 The bot

    Receives every WhatsApp message sent to a client's business number and replies automatically with buttons and lists – taking orders, booking appointments, answering questions.

    🖥️ The dashboard

    A website where the business owner and staff see orders, appointments and chats, and change everything the bot says and does – without code.

    ⏰ The scheduler

    A background timer that sends reminders, after-visit check-ins, review requests, recalls, cart reminders and broadcasts at the right time.

    One server can run many client businesses. Each business has its own WhatsApp number, products or services, texts, settings, logins and data. You (the agency) have a super-admin login that sees all of them.

    Who uses it

    PersonWhat they do
    Customer / patientOnly uses WhatsApp. Taps buttons, never installs anything.

    Agency super-admin (you)Creates client businesses, switches between them, pauses/deletes them, does WhatsApp connection.

    TermMeaning

    Meta appCreated on developers.facebook.com. Gives API access. One app can serve all your clients.
    WABA (WhatsApp Business Account)A container of phone numbers and message templates. Its ID is the "WhatsApp Business Account ID".

    Quality rating & limitsMeta rates each number from user feedback (blocks/reports). New numbers can start limited numbers of conversations per day; limits grow with quality and business verification.
    PricingMeta charges per message for templates (marketing most expensive). Customer-started service replies are mostly free/cheap. Rates change – always check Meta's official rate card before quoting.

    What happens when a customer sends "Hi"

    1. Meta sends POST /webhook to our server (src/routes/webhook.js).
    2. We check the X-Hub-Signature-256 header against the raw body with the app secret. Wrong signature → 401.
    3. We answer 200 immediately (Meta retries slow answers) and continue in the background.
    4. The business is found from metadata.phone_number_id. Unknown or paused → ignored.
    5. The message id is inserted in processed_events. Already there → duplicate (a Meta retry) → skipped.
    6. Messages are queued per customer, so two quick taps are processed in order, never in parallel.
    7. We mark the message as read and show "typing…".
    8. engine.handleIncoming() creates/updates the customer (this opens the 24-hour window), stores the message for the inbox, and loads the session (state, cart, context) from the database.
    9. The input is normalised (text, button choice, location, photo, catalogue order) and routed (section 10).
    10. The flow replies through sender.send(), which chooses normal message vs template, sends via the Graph API, and logs the result.
    11. The session is saved. If the server restarts now, the customer continues exactly where they were.
    12. The dashboard polls /api/pulse every 8 seconds and beeps for new orders, bookings, enquiries and chats needing a reply.

    10. The conversation engine

    Normalising input

    WhatsApp sendsEngine sees
    Typed text{ kind: 'text', text }
    Button tap / list pick{ kind: 'choice', id, text }
    Template quick-reply tap{ kind: 'choice', id: payload } – same ids as normal buttons
    Shared location{ kind: 'location', location }
    Photo, document, voice note, video, sticker{ kind: 'media', mediaType, mediaId }
    Order from the WhatsApp catalogue{ kind: 'order', order }
    WhatsApp Flow form reply{ kind: 'form', data }

    Routing order (first match wins)

    1. STOP / unsubscribe → customer opted out (policy). START → opted back in. Language buttons/keyword → customer language saved.
    2. Bot paused (a human is handling the chat) → stay silent and flag "needs reply" – unless the customer types menu.
    3. Global words: hi, hello, namaste, menu, help… → main menu. human, agent, talk to someone → handoff. cancel, back → cancel the current step.
    4. Closed hours with "only collect messages" setting → reply once per day and flag for the team.
    5. Button/list replies → the flow that owns the id prefix (ord:, bk:, enq:).
    6. Catalogue order → ordering.
    7. Text / location / photo during a step → the flow that owns the current state.
    8. Free text at the menu → owner quick-reply keywords → FAQ keywords → AI brain (answer / typed order / booking / handoff) → product search.
    9. Nothing matched → polite main menu. The bot is never silent and never stuck.

    11. Ordering flow internals

    MENU→ORD_BROWSE→ORD_QTY→ORD_CART→ORD_FULFIL→ORD_ADDRESS→ORD_NOTES→ORD_PAY→MENU
    • One category → it is skipped and items are shown directly. More than 10 rows → automatic "More options" pages.
    • Quantity by button (1, 2, 5) or typed number (1–99). The same product twice → quantities add up.
    • The cart is re-priced from the database before showing it and before placing the order. Out-of-stock or hidden items are removed with a message. Customers always pay today's price.
    • Minimum order is checked at checkout. Delivery fee is free above the configured amount; pickup has no fee.
    • Delivery/pickup question appears only if both are enabled. Saved address is offered ("Deliver to this address?"); a 📍 location becomes an address with a Google Maps link.
    • Only configured payment modes are offered (UPI needs a UPI ID, online needs Razorpay keys). If only one, the question is skipped.
    • createOrder() gives the next order number inside a transaction. Cash → CONFIRMED at once; UPI/online → NEW until paid.
    • Typed text while shopping → product search. Typed "cart"/"checkout" → shortcuts. With AI on, "2 kilo aata aur 1 maggi" → items added → cart shown for confirmation.

    NEWPay-now button (UPI page or Razorpay link)

    12. Booking flow internals

    MENU→BK_STAFF→BK_INTAKE→BK_DATE→BK_TIME→BK_NAME→BK_CONFIRM→MENU

    How free slots are calculated (slotsFor)

    for each staff member who does this service (or the chosen one):
    skip the day if the staff member or the whole business is on leave
    hours = staff's own weekly hours, else the business opening hours
    for each opening range of that weekday (e.g. 10:00–13:30, 17:00–20:30):
        start at the range start, step by "slot interval" minutes
        keep the slot if  start + service duration  ≤ range end
                     and  start ≥ now + minimum notice
                     and  it does not overlap an active booking of that staff member
"Any available" = all staff slots merged; booking picks the first free person.
No staff at all = the business itself is one calendar.

    Why double booking cannot happen

    book() runs in an immediate transaction (one writer at a time), re-checks overlap for each candidate staff member, then inserts. A database unique index is the last guard. If two customers tap the same slot in the same second, the second gets "Sorry, that time was just taken" with fresh times.

    Automatic timeline after booking

    Booking confirmed

    Reminder with buttons I'll be there / Reschedule / Cancel. Outside 24 h → appointment_reminder template with the same button ids.

    37. Recipe: add a new conversation flow (e.g. "Request a call back")

    1. Create the flow – src/engine/flows/callback.js:

    export const callback = {
  module: 'callback',            // name used in businesses.modules
  prefix: 'cb',                  // buttons look like "cb:…"
  states: ['CB_TOPIC'],          // states where typed text belongs to this flow

  menuItems(c) {
    return [{ id: 'cb:start', title: c.t('menu_callback'), description: c.t('menu_callback_desc') }];
  },

  async onChoice(c, [action, arg]) {
    if (action === 'start') {
      return c.buttons(c.t('callback_when'), [
        { id: 'cb:when:morning', title: c.t('callback_morning') },
        { id: 'cb:when:evening', title: c.t('callback_evening') },
      ]);
    }
    if (action === 'when') {
      c.setState('CB_TOPIC', { cb: { when: arg } });
      return c.say(c.t('callback_topic'));
    }
    return false;                  // not ours -> router shows the menu
  },

  async onText(c) {
    if (c.state !== 'CB_TOPIC') return false;
    const when = c.ctx.cb?.when;
    c.reset();
    await c.notifyOwner(`📞 CALL BACK (${when}) ${c.customer.name || ''} +${c.phone}: ${c.input.text}`);
    return c.buttons(c.t('callback_done', { when }), [{ id: 'menu', title: c.t('btn_menu') }]);
  },
};

    2. Register it – src/engine/index.js: import { callback } from './flows/callback.js'; and export const FLOWS = [ordering, booking, enquiry, callback];

    3. Allow the module – src/services/business.js: export const MODULES = ['ordering', 'booking', 'enquiry', 'callback'];

    4. Texts – add menu_callback (≤ 24 chars), menu_callback_desc, callback_when, callback_morning, callback_evening (≤ 20 chars), callback_topic, callback_done to en in texts.js.

    43. Roadmap to a self-serve SaaS

    Stage 1 – Agency (today)
    You onboard clients manually on one server. Good to ~100s of businesses.
    Stage 2 – Self-serve onboarding
    Become a Meta Tech Provider; add Embedded Signup so clients connect their own number from a Facebook pop-up (store the returned token per business – already supported). Public sign-up page creates business + owner.
    Stage 3 – Billing
    Plans and subscriptions (Razorpay Subscriptions / Stripe), usage limits per plan (messages, businesses), auto-pause on non-payment.
    Stage 4 – Scale
    Move SQLite → PostgreSQL (replace src/db/index.js with a pg pool and add await at call sites), run the scheduler as its own process, add a queue (Redis/BullMQ) behind the per-customer queue, run several web servers behind a load balancer.
    Stage 5 – Marketplace
    Templates library per industry, app integrations, white-label for resellers (brand per agency).
